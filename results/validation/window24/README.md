# 24-month validation: how it was run

`summary.md` and the JSON files here were generated by
`python -m repocompass validate --months 24 optuna/optuna sqlfluff/sqlfluff pydantic/pydantic fastapi/fastapi`
on 2026-11-04. The reading of the results, next to the 12-month ones, is in `../README.md`.

## The analyses

Each repository was analysed with a 730-day window (`REPOCOMPASS_WINDOW_DAYS=730`), so bands are made
from months -24 to -12 and tested on months -12 to 0. The other parameters were the defaults, the same
as the 12-month analyses. The run logs are in `runs/` (all values measured):

| repository | human PRs in 24 months | bot or non-user dropped | kept | wall time | API |
|---|---|---|---|---|---|
| optuna/optuna | 935 | 10 | 935 | 136.8 s | 31 requests, 50 points |
| sqlfluff/sqlfluff | 1,572 | 149 | 1,554 (sampled, see below) | 289.4 s | 74 requests, 109 points |
| pydantic/pydantic | 1,705 | 148 | 1,705 | 333 s | 115 requests, 153 points |
| fastapi/fastapi | 2,302 | 371 | 2,302 | 540.5 s | 219 requests, 273 points |

pydantic and fastapi were chosen as higher-traffic repositories; the counts above confirm they had more
PRs in the window than optuna.

Only sqlfluff was sampled: one month, 2026-10, was capped at 250 human PRs (`summary.md`), and its kept
PRs cover 2024-11-08 to 2026-11-04 (`runs/sqlfluff__sqlfluff.txt`). That month is after the cutoff
(2025-11-04), so the capping touches sqlfluff's after sample, not its before sample.

## Kept apart from the 12-month reports

The database keeps one analysis per repository, so a 24-month analysis of optuna or sqlfluff would have
replaced the 12-month report the web pages show. These analyses were therefore stored in a separate
Postgres schema, `window24`, on the same server, and read from it through Postgres' search path. To
reproduce, in order:

1. Create the schema once, for example in psql: `CREATE SCHEMA window24;`
2. In PowerShell, set `$env:DATABASE_URL` to the URL from `.env` with `?options=-csearch_path%3Dwindow24`
   appended (or `&options=-csearch_path%3Dwindow24` if the URL already has a `?`). Do not print it.
3. For the analyses only: `$env:REPOCOMPASS_WINDOW_DAYS = "730"`. `validate` reads each analysis's
   stored window, so it does not need this.
4. Run:

   ```powershell
   python -m repocompass init-db                      # creates the tables in the window24 schema
   python -m repocompass analyze optuna/optuna        # then sqlfluff/sqlfluff, pydantic/pydantic, fastapi/fastapi
   python -m repocompass validate --months 24 optuna/optuna sqlfluff/sqlfluff pydantic/pydantic fastapi/fastapi
   ```

5. Remove both variables afterwards (`Remove-Item Env:DATABASE_URL, Env:REPOCOMPASS_WINDOW_DAYS`), so
   later commands use the 12-month analyses again.

The 12-month analyses and the reports the web pages show are unchanged.
